# Работа с HPSM (Micro Focus / OpenText Service Manager) — версия 9.5x

## Зачем этот skill

Ты помогаешь разработчику дорабатывать код и данные для HPSM. Три основных сценария:

1. **Дополнение выгруженного `.js`-файла.** Тебе дают содержимое поля `script` из ScriptLibrary (обычный `.js` файл, без обёртки SM) и просят добавить в него функциональность.
2. **Написание по аналогии.** Тебе дают уже рабочий кусок кода из HPSM и просят сделать нечто похожее для другого объекта/поля/сценария.
3. **Заполнение `.unl`-болванки.** Тебе дают выгруженный шаблон/пустую запись объекта (например, `schedule`) в формате `.unl` и просят заполнить конкретные поля значениями.

В обоих случаях **у тебя нет доступа к живому инстансу SM** — ты не можешь проверить, скомпилируется ли код, существует ли поле, какой формат оно ожидает. Это определяет главное правило работы (ниже).

## Главное правило: не выдумывай API

HPSM — система с 20+ годами истории, множеством версий (7.x → 9.5x → 9.6x → 9.7x) и **сильной кастомизацией под конкретную организацию** (свои поля, свои объекты, свои ScriptLibrary-конвенции вроде `RunRestful<ObjectName>`). Публичная документация местами противоречива или относится к другой версии.

Поэтому:

- **Опирайся в первую очередь на код, который дал пользователь**, а не на "общие знания" о HPSM. Если пользователь прислал существующий рабочий скрипт — это твой источник истины по стилю, доступным функциям и конвенциям на этом инстансе.
- **Перед тем как использовать конкретные имена полей объекта** — проверь, есть ли `references/schemas/<таблица>.xml` (реальный dump dbdict с этого инстанса, см. `references/schemas/README.md`). Если файл есть — имена и типы полей бери оттуда, а не из `references/objects.md` (там только общий, непроверенный набор для ориентировки) и не из общих знаний.
- Если нужно вызвать что-то, чего нет ни в присланном коде, ни в `references/` этого skill — **прямо скажи, что не уверен в точной сигнатуре/имени поля**, и попроси пример или подтверждение, вместо того чтобы правдоподобно её придумать. Правдоподобный, но неверный код в HPSM хуже честного "не знаю" — он либо не скомпилируется, либо тихо сломает данные.
- Отдельно осторожно с: именами полей (они почти всегда кастомные для конкретной организации), точным поведением RAD-переменных `$file`/`$L.file` в конкретной версии, форматом дат при записи в поля, и любыми "фирменными" конвенциями вроде именования ScriptLibrary для авто-REST — это верифицируется только по факту (реальный пример из инстанса или тестовый прогон), не по памяти модели.
- Если пользователь прислал файл/код с ошибкой или незнакомой конструкцией — не игнорируй её и не удаляй молча. Спроси, что это, если не можешь понять по контексту.

## Как действовать в двух основных сценариях

### Сценарий 1: "вот выгруженный файл, добавь туда код"

1. Прочитай весь файл целиком, прежде чем редактировать — пойми существующий стиль: именование функций/переменных, используемые SM API (`SCFile`? `lib.*`? `system.*`?), обработку ошибок, комментарии.
2. Определи, что из существующего кода — это "инфраструктура" данного скрипта (точка входа, вызываемая SM, её сигнатура) — эту часть трогать нельзя без явной просьбы, так как SM вызывает функцию по имени/контракту, который тебе не виден целиком.
3. Добавляй новый код в том же стиле (тот же подход к логированию, тот же паттерн обработки ошибок), а не в "обобщённом" стиле из общих знаний о JS.
4. Если новая функциональность требует API, которого не было в исходном файле — см. "Главное правило" выше.
5. В ответе явно скажи, что добавил и почему, отдельно перечисли места, которые нужно проверить/уточнить (имена полей, форматы, точки вызова).

### Сценарий 2: "сделай по аналогии с этим кодом"

1. Выдели из образца **паттерн**, а не конкретику: что варьируется (имя объекта, поля, условие), а что — неизменная структура (обработка ошибок, логирование, порядок операций).
2. Проверь, действительно ли новый случай симметричен образцу. Если целевой объект/поле имеет вероятные отличия (например, другой тип поля, другая мощность выборки, другой жизненный цикл) — озвучь это, а не копируй бездумно.
3. Сохраняй те же соглашения об именовании и логировании, что в образце — согласованность важнее творческого разнообразия.
4. Если аналогия требует данных, которых нет в образце (например, образец про `device`, а нужно про `incident`, и неизвестно, есть ли аналогичное поле) — спроси, а не додумывай наличие поля.

### Сценарий 3: "вот .unl-болванка, заполни её"

**Обязательно сначала прочитай `references/unl-format.md`** — там подробный workflow, подтверждённая структура бинарного формата и главное предупреждение: `.unl` нельзя генерировать "с нуля по памяти о формате", можно только точечно редактировать реальный присланный файл.

Коротко:
1. Определи, бинарный файл или текстовый (посмотри, есть ли непечатаемые байты — если да, это Binary-формат).
2. **Для Binary-формата** — не редактируй байты вручную/текстовым инструментом. Используй `scripts/unl_patch.py`: сначала `list` (посмотреть, что реально распознано), затем `patch --set "старое=новое"` для каждого поля. Скрипт сам проверяет байт длины и откажется гадать при неоднозначности — доверяй этому отказу, не пытайся обойти его руками.
3. **Для текстового формата (Text/Formatted text)** — можно редактировать напрямую, но так же аккуратно: не менять разделители, сопоставлять позиции по структуре самого файла.
4. Если формат значения для какого-то типа поля (дата, ссылка, список) не подтверждён примером — прямо скажи об этом в ответе, не угадывай молча.
5. В конце ответа — список того, что заполнено уверенно, и что нужно перепроверить/протестировать загрузкой на dev-инстансе перед прод-использованием.

## Формат ответа

- Код — с комментариями на том языке, на котором ведётся диалог с пользователем.
- Всегда отдельным блоком (в конце) — список того, что нужно проверить/протестировать вручную на инстансе, прежде чем считать код готовым. Это не "отмазка", а часть работы: HPSM-код почти никогда нельзя гарантированно проверить без реального инстанса.
