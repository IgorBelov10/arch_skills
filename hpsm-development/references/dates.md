# Работа с датами в HPSM

## Главная находка: `XMLDate` — подтверждённый способ писать даты в поля из JS

Официально задокументированный (OpenText/Micro Focus JS reference) пример:

```javascript
var changeRequest = new SCFile("cm3r");

// Оборачиваем обычный JS Date в XMLDate
var theXMLDate = new XMLDate(new Date());

// getDatum() отдаёт значение в виде, который ожидает SM для date/time-поля
var todaysDate = theXMLDate.getDatum();
changeRequest.header.date_entered = todaysDate;
changeRequest.header.planned_start = todaysDate;

// addDuration() двигает дату по ISO 8601 duration-строке ('P7D' = +7 дней)
theXMLDate.addDuration('P7D');
var nextWeeksDate = theXMLDate.getDatum();
changeRequest.header.planned_end = nextWeeksDate;

changeRequest.doInsert();
```

Это закрывает вопрос, который раньше был помечен как неподтверждённый в `js-api.md` ("в каком виде передавать `new Date()` в поле date/time"): **подтверждённый способ — не сырой `new Date()`, а `new XMLDate(new Date()).getDatum()`.**

Подтверждённые методы `XMLDate`:
- `new XMLDate(jsDate)` — конструктор из обычного JS `Date`.
- `.getDatum()` — значение в формате, который можно присваивать date/time-полю.
- `.addDuration(строка_ISO_8601_duration)` — сдвигает дату (пример: `'P7D'` = плюс 7 дней). Общий синтаксис ISO 8601 duration (`P` + количество + единица: `Y`/`M`/`D`, и после `T` — `H`/`M`/`S` для времени) — общий стандарт, не специфичный для SM, но какие именно токены поддерживает конкретно `addDuration` на 100% этим skill'ом не протестировано за пределами примера `'P7D'` из документации. Для нестандартных сдвигов (месяцы, часы) — сначала проверить на тестовой записи.

**Важный побочный нюанс из этого же примера**, не связанный напрямую с датами, но важный для генерации кода: обращение к полям записи в примере идёт не напрямую (`changeRequest.date_entered`), а через вложенную структуру `changeRequest.header.date_entered` (с заменой точек в имени поля на подчёркивания). Это может быть особенностью конкретно составных/сложных объектов вроде change request (`cm3r`), а не универсальным правилом для всех таблиц — **не считай, что `.header.` нужно всегда**: проверяй реальную структуру объекта (через дамп dbdict, `references/schemas/`, или структуру, которую вернёт `getXML()`) перед тем как решить, плоский доступ к полю или через вложенную структуру.

## RAD-функции для работы с датами (см. полный список в `references/rad-functions-list.md`)

| Функция | Что делает |
|---|---|
| `date` | Дата-часть значения date/time (время обнуляется до 00:00:00). |
| `time` | Время-часть значения date/time. |
| `tod` | Текущие дата и время. |
| `day` / `month` / `year` | Компоненты даты независимо от формата отображения. |
| `dayofweek` | Число 1–7 — день недели. |
| `dayofyear` | День года. |
| `datecmp` | Переводит поля date/time в корректный диалект SQL (нужно при сравнении дат в запросах между разными СУБД). |
| `get.dateformat` | Формат даты текущего оператора (для отображения). |
| `get.timezoneoffset` | Разница между GMT и часовым поясом оператора. |
| `set.timezone` | Устанавливает часовой пояс. |

Эти функции — RAD-функции (см. `references/calling-rad-functions-from-js.md` про вызов из JS через `system.functions.*` и про то, что они не завязаны на интерактивный контекст, так что вызов из JS для этой группы ожидаемо осмыслен).

## Практическое правило для генерации кода

1. **Пишешь дату в поле из JS** → используй `new XMLDate(jsDate).getDatum()`, не сырой `new Date()`.
2. **Нужно узнать компонент даты (день/месяц/год/день недели)** → RAD-функции `day`/`month`/`year`/`dayofweek`/`dayofyear` через `system.functions.*`, а не парсинг строки вручную.
3. **Сравниваешь даты в SQL-запросе (`doSelect`)** → имей в виду `datecmp` для кросс-диалектной корректности, если сравнение дат ведёт себя не так, как ожидается.
4. **Читаешь дату из поля записи** (не пишешь, а читаешь) — формат возвращаемого значения этим skill'ом не проверен отдельно; не предполагай, что это будет строка в конкретном формате — выведи реальное значение (`print()`) и посмотри, прежде чем парсить его дальше.
5. **Структура доступа к полю** (`file.field` напрямую или `file.header.field_with_underscores`) — проверяй по реальной структуре объекта, не копируй паттерн `cm3r` бездумно на другие таблицы.
