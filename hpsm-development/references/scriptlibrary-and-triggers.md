# ScriptLibrary и Triggers/Scheduler

## ScriptLibrary

ScriptLibrary — объект (`Tailoring → Script Library`), хранящий переиспользуемый JS-код. Основные поля записи: `name`, `package` (группировка для удобства сопровождения), `script` (собственно код).

### Вызов функций из ScriptLibrary

- Из другого JS: `system.library.<scriptname>.<functionname>(параметры)`
- Из RAD (например, из Format Control Subroutines или из panel-процесса): через RAD-функцию `jscall()`.
- Внутри самого ScriptLibrary-файла можно вызывать функции, объявленные выше по тексту того же файла, напрямую по имени.

### Компиляция

При сохранении ScriptLibrary можно скомпилировать код (кнопка Compile) — это только синтаксическая проверка (аналог "собирается ли"), она **не гарантирует**, что код будет корректно работать в рантайме (не проверяет существование полей, объектов, прав доступа и т.д.).

### Конвенция `RunRestful<ObjectName>` (не универсальная, проверять на месте)

В части инстансов SM используется соглашение: ScriptLibrary с именем вида `RunRestful<ObjectName>` автоматически регистрируется как обработчик REST-запросов к соответствующему бизнес-объекту (SM сам открывает REST endpoint на основе имени библиотеки). Это **не задокументированная универсально** в открытых источниках Micro Focus вещь — по всей видимости, либо связана с конкретной конфигурацией External Access/REST API Framework, либо это специфика конкретной сборки/версии.

**Что это значит на практике:**
- Если в организации такая конвенция подтверждена (есть хотя бы один реальный рабочий пример `RunRestful*`) — используй его как эталон сигнатуры входной функции (как называется точка входа, что приходит на вход — весь объект запроса целиком или отдельно `method`/`body`/`params`, что ожидается на выходе).
- Не изобретай сигнатуру с нуля "по аналогии с общими REST-фреймворками" — на разных инстансах она может отличаться.

## Triggers / Scheduler

SM позволяет запускать код по расписанию или по событию через объекты уровня `Scheduler`/`Schedule Records` (в разных версиях/конфигурациях могут называться по-разному — "Scheduled Records", "Scheduler Records"). Такая запись обычно указывает:

- какую RAD-процедуру или JS-функцию (через ScriptLibrary) вызвать,
- когда/как часто (интервал, cron-подобное расписание, или условие-триггер),
- какие входные параметры передать.

**Практический момент для массовых операций** (как в задаче с обновлением системного времени по устройствам): такие операции обычно логично оформлять именно как Scheduler-запись, вызывающую ScriptLibrary-функцию, а не как FC-хук, который сработает на каждое сохранение записи — иначе легко случайно навесить тяжёлую логику на путь обычного пользовательского сохранения записи и просадить производительность формы.

## Общие рекомендации по стилю кода в ScriptLibrary

- Логирование/вывод — через `print(сообщение)` (подтверждено на этом инстансе, см. `js-api.md`; `lib.logmessage` на этом инстансе не работает).
- Оборачивать операции записи в try/catch — ошибки SM API не всегда выбрасывают JS-исключение "красиво", иногда возвращают код ошибки (см. `references/rad-language.md` про RC-коды) вместо исключения — проверяй оба варианта, если не уверен, как ведёт себя конкретный вызов.
