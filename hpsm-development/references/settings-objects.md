# Прочие настроечные объекты SM

Format Control и ScriptLibrary разобраны отдельно (`format-control.md`, `scriptlibrary-and-triggers.md`). Здесь — остальные настроечные объекты уровня Tailoring.

**Важно про уровень уверенности:** имена таблиц `format`, `formatctrl`, `displayoption`, `extaccess`, `ioaction`, `triggers`, `wizard` в этом файле **подтверждены реальным примером** — они встретились как имена таблиц-целей внутри поля `record` в присланном пользователем `.unl` (unload-задание `test_SD`, см. `unl-format.md`). То есть эти таблицы точно существуют на разбираемом инстансе SM. Их **внутренняя структура полей и точная семантика** ниже — общие знания о HPSM, не проверенные на этом инстансе построчно — придерживайся того же правила, что и везде в этом skill: не выдумывать точные имена полей, если нет реального примера записи.

## Format (`format`)

Определение экранной формы: какие поля показывать, в каком порядке/расположении, элементы управления (текстовое поле, список, кнопка и т.д.), связь с Format Control (FC привязывается к `Application`/`Format`, см. `format-control.md`). Обычно редактируется через Forms Designer в UI, а не напрямую как код — если пользователь просит "поправить форму", скорее всего речь о визуальном редакторе, а не о тексте, который можно патчить как ScriptLibrary.

## Triggers (`triggers`)

Триггеры уровня файла — привязка логики к событию изменения записи (add/update/delete), независимо от того, через какую форму или API пришло изменение (в т.ч. изменения из JS/интеграций/фоновых заданий — в отличие от Format Control, который в первую очередь завязан на форму).

В присланном примере видно реальную конвенцию именования триггеров (5 отдельных условий): вида `<область>.<событие>.<описание>`, например `rzd.b.a.hpcrequest.osc.add`, `hpc.hpcrequestvp.a.u.unsuspend.related`. Похоже на паттерн `<префикс проекта>.<b/a — before/after>.<a/u — add/update>.<объект>.<описание>`, но это гипотеза по наблюдению за именами, а не подтверждённая документацией схема — если нужно писать новый триггер, лучше свериться с несколькими существующими именами на этом же инстансе и повторить их структуру, а не изобретать новую.

## Display Options (`displayoption`)

Условное отображение элементов формы (поле/кнопка/панель показывается или скрывается/блокируется в зависимости от RAD-условия). В примере видно использование `id="..."` (конкретный элемент формы по идентификатору) и `id isin {...}` (список идентификаторов, к которым применяется одно условие) — та же логика "условие в стиле RAD", что и в Format Control (см. `rad-language.md` про функции и синтаксис условий).

## External Access (`extaccess`)

Определения внешнего доступа — экспонирование объекта/сервиса наружу (Web Services/REST). В примере: `service.name#"OSC"` — условие отбора по имени сервиса. Это, вероятно, тот самый механизм, который стоит за конвенциями вида `RunRestful<ObjectName>`, обсуждавшимися ранее (см. предупреждение в `scriptlibrary-and-triggers.md`) — если нужно разобраться, как конкретно на этом инстансе настроен REST-доступ к объекту, стоит открыть реальную запись `extaccess` для этого сервиса, а не полагаться на общее описание.

## IO Action (`ioaction`)

Действия интеграционного слоя — как правило, используется для маппинга исходящих/входящих событий в сценариях интеграции (например, e-bonding между несколькими SM-инстансами или внешними системами). В примере видно отбор по имени: `name isin {"Rzd.SD.Request.VPKC","Rzd.SD.Probsummary.VPKC","DDC.RQVP.Unsuspend.Related"}`.

## Wizard (`wizard`)

Многошаговые формы-мастера (последовательность экранов для сложного сценария ввода данных, например создания нескольких связанных записей за один проход). В примере: `name isin {"Rzd Mass RQVP Create From Change - 2"}`.

## dbdict

Словарь базы данных — определение структуры таблицы: список полей, их типы (`VARCHAR2(70)`, `CHAR(1)`, `FLOAT`, `DATE`, `CLOB`, `BLOB` и т.п. — эти типы видны прямо в разобранном примере `unload_test_SD.unl`, в блоке `descriptor`), индексы, ключи. Это фундаментальный объект — почти все остальные настроечные объекты (Format, FC, Triggers, ScriptLibrary-обращения к данным) в конечном счёте оперируют полями, описанными в dbdict конкретной таблицы.

**Практическое следствие:** если нужно узнать реальные имена и типы полей объекта (например, `device` или `schedule`) — самый надёжный источник это dbdict-описание этой таблицы (в самом SM, `System Definition → Tables`, либо в реальном `.unl`-экспорте этой таблицы — структура `descriptor`-блока в вашем примере это и есть сериализованный кусок dbdict). Не полагайся на "типичный набор полей" из `references/objects.md` без сверки, если задача требует точных имён для записи данных.

## Link

Определения связей между таблицами/записями — related records, переходы между объектами (например, связь Incident → Problem → Change, или CI → связанные инциденты). Обычно используется для настройки того, что показывается на вкладке "Related Records"/аналогичной панели формы, и для навигационных меню между связанными записями.

## Итоговое правило для всех объектов на этой странице

Для любого из этих объектов: если задача — не "объяснить, что это" (для этого достаточно текста выше), а "написать/изменить конкретную запись/условие" — запрашивай реальный пример записи этого объекта с этого же инстанса, прежде чем предлагать конкретный синтаксис. Общее описание назначения объекта — надёжно; конкретные имена полей и точный синтаксис условий внутри — нет.
