# Join files (join dbdict) — общий механизм

## Что это (подтверждено несколькими независимыми обсуждениями на community.microfocus/opentext)

Обычная таблица (dbdict) в SM хранит все свои поля в одной физической структуре. Иногда часть данных, логически относящихся к одной записи, физически разнесена по **нескольким таблицам** (например, общие атрибуты — в одной таблице, атрибуты конкретного подтипа/варианта — в другой). Чтобы работать с этим как с одной записью, SM использует **join file (join dbdict)** — логический файл на уровне dbdict, который на уровне SQL реально джойнит несколько физических таблиц (**inner join**, выполняется силами СУБД; тип и поля джойна зафиксированы в определении самого join-файла, не выбираются на лету в конкретном запросе).

Подтверждённый конкретный пример такого join-файла: **`joincomputer`** — джойн таблиц `device` и `computer` (используется для CI-подтипа "компьютер"). Это не абстрактная иллюстрация, а реально встречающееся в нескольких независимых источниках имя join-файла — на нём ниже показаны все механики.

## Практические следствия использования join-файла

### 1. Вставка одной операцией сразу в обе физические таблицы

Если запись целиком относится к одному join-файлу (все нужные поля укладываются в его определение), можно **вставлять запись напрямую в join-файл** — это заполнит сразу обе физические таблицы за одну операцию, вместо раздельной вставки в каждую таблицу по очереди.

### 2. Обычные списки/QBE по умолчанию работают с базовой таблицей, а не с join-файлом

Стандартный список/QBE по умолчанию строит запрос к **базовой физической таблице**, а не к join-файлу — это подтверждено через RAD-дебаггер (`d $L.filed` в QBE-списке показывает именно базовую таблицу, не join). Значит, поля, которые физически лежат только во второй таблице join-а, **не видны и не доступны для поиска** в обычном списке, пока список/формат явно не переключён на join-файл — а это уже отдельная кастомизация форм/QBE.

**Практический вывод для генерируемого кода:** если нужно читать/фильтровать по полю, которое физически лежит не в базовой таблице, а во второй таблице join-а — открывать нужно `new SCFile("<имя join-файла>")`, а не базовую таблицу, иначе поле просто не будет доступно в объекте записи.

### 3. Синтаксис обращения к полю join-файла из другого места (RAD/отчёты)

Подтверждённый синтаксис для ссылки на поле из присоединённой (второй) таблицы join-а: `file.<имя dbdict>,<имя поля>`. Важная оговорка, тоже подтверждённая практикой: **это работает только для таблиц, реально входящих в join** — попытка так же сослаться на поле таблицы, которая физически в join не участвует (см. ниже), не сработает.

### 4. Не путать join dbdict с "виртуальным" джойном для отображения на форме

На форме иногда показываются поля из таблиц, которые **не входят в реальный join dbdict**, а подтягиваются только для отображения ("virtual join") — реальный подтверждённый пример: поле, физически хранящееся в одной таблице, показывается на форме записи из другой таблицы через такой виртуальный механизм, без настоящего join dbdict между ними. Для таких полей:
- синтаксис `file.<dbdict>,<field>` **не работает** (подтверждено неудачной попыткой в реальном обсуждении);
- обращаться к таким данным в коде нужно явным отдельным запросом к исходной таблице, а не рассчитывая, что она "присоединится" как в join-файле.

**Не путай эти два механизма** при генерации кода — если непонятно, входит ли нужное поле в реальный join-файл или подтягивается только визуально, нужно проверить (см. ниже), а не предполагать.

## Как узнать реальный список и состав join-файлов на конкретном инстансе

1. `System Definition → Tables` — там join-файлы видны как отдельный тип таблиц.
2. Дамп dbdict конкретного join-имени тем же способом, что уже есть в этом skill: `new SCFile("dbdict").doSelect('name="<имя join-файла>"')` + `DumpDbdictJson` (см. `examples/dump-dbdict-json.md`) — покажет реальный состав полей объединённой записи.

## JS API: `SCFile.join()`

В официальном JS Programming Guide для SM в списке методов `SCFile` есть метод с названием **`SCFile.join()`** — само существование метода с этим именем подтверждено (встречается в оглавлении официального руководства). Точные параметры и семантика этого метода этим skill'ом **не проверены** — если нужно выполнить программный join из JS (а не через готовый join dbdict), сначала сверься с описанием метода в актуальной версии руководства/протестируй на dev-инстансе, а не полагайся на предположение о сигнатуре.

## Итоговое правило для генерации кода

1. Нужное поле физически лежит не в базовой таблице объекта, а во второй таблице join-а → используй `new SCFile("<join-файл>")`, не базовую таблицу.
2. Не уверен, входит ли поле в реальный join, или это virtual join для отображения → проверь дампом dbdict, не гадай.
3. Массовая загрузка записей, целиком укладывающихся в один join-файл → вставка сразу в join-файл, раздельная вставка в обе таблицы не нужна.
4. Списки/поиск по умолчанию видят только базовую таблицу — если нужен поиск по полю второй таблицы join-а, это требует изменения формата/QBE, а не просто смены таблицы в коде выборки.
