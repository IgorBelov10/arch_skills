# Работа с .unl файлами (выгрузка/загрузка через Database Manager)

## Что это, честно про уровень уверенности

`.unl` — нативный формат экспорта/импорта данных SM (используется в `Tailoring → Database Manager` для Export/Import отдельных записей или целых таблиц/объектов, включая служебные таблицы вроде `unload`, `schedule` и т.д. — принцип формата один и тот же независимо от того, какой объект выгружается). Официально подтверждено (документация Micro Focus):

- SM поддерживает несколько режимов экспорта: **Binary**, **Text**, **Formatted text**. Какой из них получите вы, зависит от того, как делалась выгрузка (по умолчанию через Database Manager обычно получается **Binary**).
- Файл содержит **описание dbdict** (структуры таблицы) плюс сами записи.

## Подтверждённая структура для Binary-формата (разобрано по реальному байтовому примеру)

На реальном примере (`unload_test_SD.unl`, запись таблицы `unload`) подтверждено побайтовым сравнением:

```
[1 байт: длина строки N, значение 0..255] [N байт самой строки] ["/" как разделитель после значения]
```

То есть перед каждым строковым значением (именем поля, именем таблицы, RAD-условием и т.д.) стоит **один байт длины**, дальше — сами байты значения. Это подтверждено точным совпадением: байт `0x82` (=130) стоял перед строкой ровно из 130 символов.

**Что НЕ подтверждено и остаётся неизвестным:**
- Смысл остальных управляющих байтов между значениями (`0x90`, `0x91`, `0x2f`, `0x40`, `0x2c` и т.п.) — похоже на маркеры типов/структуры dbdict, но точная грамматика не расшифрована.
- Есть ли где-то в файле **внешний счётчик общей длины записи/файла**, который не будет автоматически совпадать после изменения длины одной строки. Мы это не проверяли на реальной загрузке.
- Поведение для строк длиннее 255 байт (однобайтовая схема длины физически не может закодировать больше 255) — вероятно, есть отдельная многобайтовая схема, но пример на неё не наткнулся.

## Инструмент: `scripts/unl_patch.py`

Это следствие честной оценки выше: раз обычный "прочитать/переписать текстом" подход для Binary-формата небезопасен (одна неверно пересчитанная длина ломает файл), в skill есть готовый Python-скрипт для **точечной** правки:

```bash
# посмотреть, какие length-prefixed строки распознаются в файле (только чтение, ничего не меняет)
python3 scripts/unl_patch.py list path/to/file.unl

# заменить одно или несколько значений, с автоматическим пересчётом байта длины
python3 scripts/unl_patch.py patch path/to/file.unl path/to/output.unl \
    --set "СТАРОЕ_ЗНАЧЕНИЕ=НОВОЕ_ЗНАЧЕНИЕ" \
    --set "ЕЩЁ_ОДНО=ЗНАЧЕНИЕ"
```

Как использовать в сценарии "заполни .unl-болванку":

1. Сначала `list` — получить список того, что реально распознано как строки в файле (это подсказка, не гарантированно полный список полей — часть "находок" может быть случайным совпадением байтов).
2. Сопоставить нужные позиции/значения с тем, что просит пользователь.
3. Вызвать `patch` с точными `--set` заменами. Если значение в файле встречается несколько раз (скрипт сообщит об этом явно и откажется гадать) — нужно взять более длинный, уникальный фрагмент old-value (например, включить кусок соседнего текста), либо явно уточнить у пользователя, какое из вхождений менять — скрипт **осознанно** не патчит неоднозначные совпадения молча.
4. **Всегда** предупреждать пользователя: протестировать загрузку патченного файла на dev/test инстансе перед прод-использованием — скрипт не может гарантировать целостность файла за пределами того, что подтверждено (см. "не подтверждено" выше).

## Если формат оказался текстовым (Text / Formatted text export)

Тогда применим более простой подход:

1. Не переформатируй файл, работай с реальными разделителями, которые видишь.
2. Сопоставляй позиции значений с именами полей по структуре внутри самого файла, не по предположениям.
3. Заполняй только те позиции, для которых пользователь дал значение.
4. Формат значения (дата, ссылка на запись, список/enum) может не совпадать с тем, что видно в UI — если есть другой непустой пример того же типа поля, использовать его как эталон.

## Если пользователь просит собрать `.unl` с нуля (не из болванки/примера)

Не делать этого напрямую — предложить взять реальный экспорт хотя бы одной существующей записи как основу, либо создать запись через UI/ScriptLibrary и затем выгрузить средствами самого SM.

## Пример корректного ответа модели (шаблон формулировки)

> Определил формат файла как Binary (length-prefixed строки, см. `unl_patch.py`). Заменил значение `test_SD` на `<новое имя>` — оно встречалось в файле один раз, длина байта пересчитана автоматически.
> Значение `<поле>` не тронул — оно встречается в файле дважды с одинаковым текстом, и я не уверен, какое из двух относится к нужному вам полю. Уточните, пожалуйста, или дайте больше контекста для однозначного совпадения.
> Перед использованием в проде — протестируйте загрузку файла на dev-инстансе: пересчёт байта длины подтверждён для одной строки, но полная грамматика файла не расшифрована, и я не могу гарантировать отсутствие скрытых зависимостей (например, общего счётчика длины записи).
