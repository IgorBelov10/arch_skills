# Format Control (FC)

## Что это

Format Control — механизм привязки логики (без обязательного JS — на RAD-выражениях) к форме/файлу: срабатывает при открытии записи, Add, Update, Delete. Используется для валидаций, вычисляемых полей, доп. запросов к другим файлам, вызова RAD-подпрограмм.

**Не злоупотреблять**: официальная рекомендация Micro Focus — не переусердствовать с FC для тяжёлой кастомизации (это снижает производительность); для сложной логики лучше Data Policy/Process Designer/ScriptLibrary.

## Где искать в UI

`Tailoring → Format Control` (или через поиск в System Navigator). Запись FC привязана к конкретному файлу (`Filename`/`Application`, например `device`).

## Структура записи FC — 4 основные панели

### 1. Additional File Queries

Дополнительные запросы к этому же или другим файлам, результат кладётся в переменные `$file`, `$file2`, `$file3`... (нумерация — по порядку строк в панели).

Поля строки: `Filename` (в каком файле искать), `Query` (условие выборки), плюс условия `Add`/`Update`/`Delete`/`Display` (когда этот запрос вообще выполняется).

### 2. Calculations

Вычисление значения поля на основе других полей/запросов. Аналогичная структура условий Add/Update/Delete/Display + выражение.

### 3. Validations

Проверка условия, блокирующая сохранение при false.

Поля строки:
- `Add`/`Update`/`Delete`/`Display` — RAD-выражение (true/false): **когда** сработает проверка.
- `Validation` — RAD-выражение (true/false): **что** проверяем. `false` → ошибка.
- `Msg` — текст сообщения об ошибке.
- `Focus` — на какое поле поставить курсор при ошибке.

### 4. Subroutines

Вызов RAD-подпрограмм (в т.ч. через `jscall()` для вызова JS из ScriptLibrary) с теми же условиями Add/Update/Delete/Display.

## Пример: обязательность и формат поля `logical.name` в `device`

Validation-строка:

- Add: `true`
- Update: `true`
- Validation: `not(null(logical.name)) and index(rtrim(logical.name)," ")=0`
- Msg: `Logical Name обязателен для заполнения и не должен содержать пробелов`
- Focus: `logical.name`

Разбор RAD-функций: см. `references/rad-language.md`.

## Проверка на уникальность значения поля в рамках того же файла

Общая идея: в Additional File Queries сделать запрос по тому же файлу на совпадение значения поля, **исключив текущую редактируемую запись** (иначе запись всегда найдёт сама себя). Дальше в Validations проверяется, вернулся ли результат запроса ($fileN).

**Важно:** точный синтаксис самоисключения текущей записи через `$L.file` (переменная текущей редактируемой записи, в отличие от `$file`/`$fileN` — результатов Additional Queries) может отличаться по поведению между Add (записи ещё нет в базе) и Update (запись уже есть, у неё есть свой ключ). Это стоит протестировать на конкретном инстансе перед продом, а не полагаться на одну "универсальную" формулу — в этом skill сознательно не приводится "единственно верная" формула для этого случая.

## Общие RAD-переменные, встречающиеся в FC (см. подробнее rad-language.md)

- `$file`, `$fileN` — результаты запросов из Additional File Queries.
- `$L.file` — поля текущей редактируемой записи (той, на которую сработал FC).
- `$G.*` — глобальные переменные сессии (например `$G.ess` — признак ESS-пользователя в некоторых конфигурациях).
