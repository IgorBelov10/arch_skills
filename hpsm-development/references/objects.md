# Основные бизнес-объекты HPSM

## Общий принцип

Каждый "объект" в SM — это файл в базе данных (dbdict), описываемый в `System Definition → Tables`. Реальный набор полей **всегда кастомизирован** под конкретную организацию: стандартные поля из коробки почти всегда дополнены своими (`u_*`, `custom.*` — конвенция именования кастомных полей тоже своя у каждой организации). Ниже — типовой (out-of-the-box) состав, который нужно рассматривать как отправную точку, а не как гарантированный список полей на конкретном инстансе.

## Interaction (интеракция / обращение)

Точка входа для Service Desk. Регистрируется первый контакт с пользователем, дальше может эскалироваться в Incident, Problem, Change или Request.

Типичные поля: `id` (номер обращения, например IM10013 в некоторых конфигурациях), `title`/`description`, `category`, `service`, `contact.name`, `assignee`, `status`/`phase`.

## Incident (инцидент)

Нарушение нормальной работы сервиса. Жизненный цикл управляется через `phase`/`status` поле (значения вроде Open/Categorize/Assign/... — конкретный набор фаз конфигурируется через Process Designer, если он используется).

Типичные поля: `incident.id`, `category`, `area`, `subarea`, `assignment.group`, `assignee`, `urgency`, `priority`, `impact`, `open.time`, `close.time`, `closed.by`, `affected.item`/`device` (связь с CI).

## Problem (проблема)

Управление корневыми причинами повторяющихся инцидентов. Часто связан с Incident через related-таблицы (какие инциденты вызваны данной проблемой).

## Change (изменение)

Управление изменениями. В версиях с Process Designer жизненный цикл определяется фазами (workflow), а не жёстко зашитыми статусами — если в организации используется Process Designer для change, статус/фаза объекта настраивается там, а не в Format Control.

## Device / CI (конфигурационная единица, CMDB)

Хранит конфигурационные единицы — устройства, серверы, приложения и т.д. Обсуждавшееся ранее поле `logical.name` — это как раз поле объекта `device`, используемое как человекочитаемый уникальный идентификатор CI.

Типичные поля: `logical.name`, `status`/`istatus` (эксплуатационный статус, например Active/Disposed/Retired — точные значения кастомны), `location`, `owner`, `ip.address` (может быть в кастомном или связанном поле), `assignment.group`.

**Важно:** название и структура полей IP-адреса, владельца и т.д. в реальных инстансах почти всегда кастомные (см. предыдущий разговор про 5 полей для REST-интеграции) — не полагайся на конкретные имена без проверки.

**Про подтипы CI (компьютеры, сетевое оборудование и т.д.):** специфичные для подтипа поля лежат не в `device`, а в join-файле вроде `joincomputer` — см. `references/joinfile.md` (общий механизм join-файлов), там же про разницу между реальным join dbdict и "виртуальным" джойном для отображения на форме.

## Request (запрос на обслуживание / Service Catalog)

Оформление запроса из каталога услуг. Часто связан с Change (если запрос требует изменения) через related tables.

## Общие для всех объектов служебные поля (обычно есть везде)

- `sysmodtime` — время последнего изменения записи
- `sysmoduser` (или похожее) — кто последний изменил
- `dbdict`-уровневые уникальные ключи (не всегда `id`, зависит от объекта)

## Как узнавать реальную структуру конкретного объекта

Если пользователь не прислал реальные имена полей/пример кода для нужного объекта — **спроси**, какие поля реально есть, или попроси экспорт dbdict/пример существующего скрипта, работающего с этим объектом. Не изобретай "вероятные" имена полей для write-операций (для read/интерпретации кода это менее критично, чем для генерации нового кода, который должен реально сохраняться).
